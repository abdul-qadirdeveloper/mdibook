# Plan: incident 003, reschedule conflicts (one stream)

## Context

Incident INC-20261015-0415: reschedules lost their slot more often than usual, and callers mostly resent the slot they had just lost. Spec 003 (draft) keeps today's 409 `SLOT_TAKEN`. It fixes the message for moves, offers the 3 open slots nearest the taken one (not the next 3 after it), adds `Idempotency-Key` to reschedule, and writes an ids-only `reschedule.conflict` log line with a server-computed `sameSlotRetry` flag. There are no screen changes.

Decisions made in this session (record them in spec section 5 before coding):
- **F5 → (a)**: include R12 (RescheduleRequestKey table plus a new migration).
- **F9 → (a)**: a session is the signed-in user id. Lost slots are remembered for 15 minutes in an in-process map, with nothing persisted.

Preconditions before any code: **F7** is authorized (this is a Stream 0 change set, in its own PR with both required checks; main is protected), and the spec status moves from draft to approved. F1 and F8 don't block code.

## Where SLOT_TAKEN comes from today

- `src/lib/appointments/core.ts:306`: inside the move transaction, `checkBookable` reports `occupied`, so it throws the private `SlotTaken`.
- `src/lib/appointments/core.ts:358-359`: the `catch` turns `SlotTaken`, **or any** unique violation (`violatedUniqueIndex(error) !== null`), into `await slotTaken(doctorId, newStart, now)`.
- `src/lib/appointments/core.ts:42-51`: `slotTaken()` builds `new AppError("SLOT_TAKEN", { nextSlots, timeZone })` from `nextOpenSlots` (next 3 *after* the wanted start, `src/lib/open-slots.ts:95`).
- The message is fixed per code: `src/lib/errors.ts:12-15` ("…Nothing was booked…"), applied by `errorBody` (`errors.ts:104`). `src/lib/route.ts:147-149` maps it to the 409 and logs `request.failed.SLOT_TAKEN` with `requestId` and `actorId` only.

## Files that change

Production:
- `src/domain/slots.ts`: add a pure `nearestSlots(open, target, count, exclude)`. It ranks by |start − target| (on a tie, the earlier one wins), drops the excluded starts, takes `count`, and returns them earliest first (R3, R4).
- `src/lib/open-slots.ts`: add `nearestOpenSlots(client, doctorId, target, count, now, exclude)`. It widens a window around `target` in 14-day steps, clamped to now and the booking horizon, until it holds ≥ `count` slots or covers the whole range, then calls `nearestSlots`. It uses `listOpenSlots`, the same function the `GET /doctors/{id}/slots` route uses (`src/lib/patient/search.ts:325`), so R4 holds by construction. The loop lives here because `tests/architecture.test.ts` forbids loops in core.
- `src/lib/errors.ts`: add a fixed table of SLOT_TAKEN message variants (`booking` = today's text unchanged, `reschedule` = R2, `rescheduleNoSlots` = R5). Add an optional `messageVariant` to `AppError`, and let `errorBody` take it. The code stays `SLOT_TAKEN` and the status stays 409.
- `src/lib/route.ts`: line 149, pass `error.messageVariant` through `fail()` to `errorBody`. Nothing else changes: the `Idempotency-Key` header is already parsed and validated (`route.ts:123-129`) and handed to the handler as `idempotencyKey`, together with `requestId`.
- `src/lib/logger.ts`: allow one non-id key, `sameSlotRetry`, whose value must be a boolean. The signature `(event: string, ids?: LogIds)` stays, so the architecture test still passes. Any other non-id key is still refused.
- `src/lib/appointments/lost-slots.ts` (new): the in-memory per-user record of slots lost to `SLOT_TAKEN`, kept as `{doctorId, startMs, lostAt}` for 15 minutes and pruned on access. `hasLost(userId, doctorId, start, now)` and `recordLost(...)`. Only `now` is injected (fixed clock in tests). It never logs anything.
- `src/lib/appointments/core.ts`: `rescheduleAppointment` (details in Order of work, step 7). All appointment writes stay here.
- `src/lib/patient/reschedule.ts`, `src/lib/clinic/reschedule.ts`: take `requestId` and `idempotencyKey` and pass them on to `rescheduleAppointment`.
- `src/app/api/v1/appointments/[id]/reschedule/route.ts`: pass `requestId` and `idempotencyKey` from the route context. The 200 response stays `{ appointment: await readAppointment(session, result.appointmentId, now) }`.
- `prisma/schema.prisma`: add a `RescheduleRequestKey` model (actorId, clinicId, appointmentId, idempotencyKey VarChar(100), requestedStartsAt, outcome enum `moved | slot_taken`, createdAt), `@@unique([actorId, idempotencyKey])`. It has no free-text fields.
- `prisma/migrations/<timestamp>_reschedule_request_key/migration.sql` (new): generated by `make migrate`. No committed migration is edited.

Tests and docs:

- `tests/integration/foundation/logger.test.ts`: tests for the `sameSlotRetry` flag.
- `tests/integration/incident-003/reschedule-conflicts.test.ts` (new): the main proof file.

1. **Preconditions**: F7 authorized, the spec records F5(a)/F9(a) and is approved. Work on `incident/reschedule-conflicts`.
2. **Failing tests first**: write `reschedule-conflicts.test.ts`, the `nearestSlots` unit tests and the logger flag tests. Run `make test` and show they fail for the expected reasons (old message, next-after slots, no log line, header ignored). Those new tests are not edited afterwards.
3. **Domain**: `nearestSlots` in `src/domain/slots.ts` gets the unit tests passing.
4. **Lookup**: `nearestOpenSlots` in `src/lib/open-slots.ts`.
5. **Message and log plumbing**: the `errors.ts` variants, then the one-line pass-through in `route.ts`, then the boolean flag in `logger.ts`.
6. **Storage**: the `RescheduleRequestKey` schema and a new migration (`make migrate`), plus `lost-slots.ts`.
7. **Core** (`rescheduleAppointment`):
   - The first scoped read also selects `clinicId` and `startsAt`. Out of scope is still `NOT_FOUND` first (R8).
   - Inside the transaction, after `lockAppointment`, look up the key (actor plus key, under 24h). If it was stored for a different appointment or start, raise `validationError({ field: "Idempotency-Key", problem: "invalid" })`. A stored `moved` returns `{ appointmentId }`. A stored `slot_taken` re-applies the patient window check, then raises a fresh conflict. Because the lookup happens under the appointment row lock, two copies of one submission sent together are serialized: the second sees the first one's key.
   - The window check comes before the slot check, as today (R8).
   - On success, write the key row (`moved`) in the same transaction as the move (spec section 3, rule 2).
   - In the `catch`, treat only `SlotTaken`, or a violation of `Appointment_one_active_per_doctor_start`, as a conflict. Any other unique violation is rethrown. Then: compute `sameSlotRetry = hasLost(...)`, call `recordLost(...)`, insert the `slot_taken` key row if a key was sent (`ON CONFLICT DO NOTHING`), write `logger.warn("reschedule.conflict", { requestId, doctorId, clinicId, sameSlotRetry })` once, and throw the rescheduling conflict. It uses `nearestOpenSlots` with the taken start and the current start excluded, and the variant `reschedule` (or `rescheduleNoSlots` when the list is empty).
   - The booking path keeps `slotTaken()` and the `booking` message, untouched (out of scope).
8. **Thread through**: the patient and clinic reschedule use cases, then the shared route, then the `api.ts` helper.
9. **Adjust** the two existing next-slot assertions to the nearest-slot values.
10. **Verify**: `make check` passes. Run the `verifier` agent against spec 003, then open a PR to `main`.

## Risks

- **Frozen files (F7).** `core.ts`, `errors.ts`, `route.ts`, `logger.ts`, `open-slots.ts`, `slots.ts`, `schema.prisma` and the shared reschedule route are Stream 0 files. If F7 isn't authorized, stop.
- **Unique-violation mapping.** Today any P2002 becomes `SLOT_TAKEN` (`core.ts:359`). With a second unique index in play, a key collision would be misreported. Restrict the mapping to the named appointment index.
- **The architecture test forbids loops and the word `retry` in `core.ts`.** Keep the search loops in `open-slots.ts` and `lost-slots.ts`. Name the local variable something like `lostBefore` (the `sameSlotRetry` key has no word boundary, so the regex doesn't match it, but avoid anything closer).
- **In-memory lost-slot store (F9 a).** It resets on restart and isn't shared across instances, so `sameSlotRetry` undercounts in a multi-instance deploy. That's acceptable for the dev stand-in. Revisit with real sessions (F9 b).
- **Two log lines per conflict.** `route.ts:148` still writes `request.failed.SLOT_TAKEN` (info). R13 asks for exactly one `reschedule.conflict` line, and the tests count that event only.
- **Replays.** A replayed `slot_taken` writes no new `reschedule.conflict` line, because no move was attempted. A replay inside the patient window gets `RESCHEDULE_WINDOW_CLOSED` (R8 takes precedence over R12). Both are interpretations, so note them in the PR.
- **The key row is bookkeeping, not an audit event.** R10 forbids audit and notification rows on a conflict. The key row is the only write, and only when a key is sent.
- **The nearest-slot search cost.** In the worst case it widens to the full 90-day horizon, a few thousand generated slots for one doctor. That's cheap, but it adds work on the 409 path.
- **The logger change is a privacy surface.** Allow exactly one boolean key, and keep the refusal of all other non-id fields (R18).

## Options rejected

- **A new error code** (e.g. `RESCHEDULE_SLOT_TAKEN`) for the new message: R1 requires the code and status to stay `SLOT_TAKEN`/409.
- **Passing `message` inside `ErrorDetails`**: messages must stay in the fixed table in `errors.ts` (R88). Free strings from call sites would bypass that.
- **Writing the conflict log line in `route.ts` or the route handler**: only core knows the doctor, the clinic and whether the request was a conflict, and route.ts is shared by every route.
- **Putting the nearest-slot logic in `src/lib/patient` / `src/lib/clinic`**: both roles need identical lists (R19), and core builds the error.
- **Loading all 90 days of slots in one query**: simpler, but it's always the worst-case cost. Rejected in favor of the widening search.
- **A database table for lost slots, or a per-user store with no time limit**: F9 options you declined in this session.
- **Logging the requested start or a hash of it**: F2, resolved against.
- **Retrying the slot, or auto-moving the appointment to a listed slot**: R7 and the CLAUDE.md rule.
